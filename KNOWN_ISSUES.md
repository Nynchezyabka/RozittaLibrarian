## Критические баги (ломают основной сценарий)

### BUG-001 — Счётчик сообщений = 0 на главной странице

**Severity:** critical
**Класс:** П3 (карточка = счётчик из БД, не из паспорта) — нарушение
**Где:** `core/archive.py` (card to_dict), `core/librarian_core.py`

**Симптом:**
На главной странице с карточками архивов для реальных архивов
(не демо) показывается «0 сообщений». При этом `/api/archives/{id}/inspect`
возвращает корректное число (16 495 для МГ).

**Воспроизведение:**
1. Добавить реальный архив (через «+» в левом сайдбаре, указать
   путь к папке с `telegram_archive.db`)
2. Вернуться на главную (`#/`)
3. На карточке нового архива — «0 сообщений»
4. Открыть `http://localhost:8011/api/archives/{id}/inspect` —
   показывает 16 495

**Корневая причина (предположительно):**
`archive_card.to_dict()` берёт `messages_count` из `archive_passport.json`,
а у реального архива этого поля нет или оно 0. Должен брать из
`parser_db.count_messages()`.

**Ожидаемый фикс:**
В `to_dict()` вызвать `parser_db.count_messages()`, если парсер-БД
доступна. Фолбэк на паспорт — только если БД нет.

**Регрессионный тест:** `test_card_count_from_db_not_passport`

### BUG-002 — Изоляция архивов: открытый архив B показывает данные A

**Severity:** critical
**Класс:** П4 (изоляция архивов — никакого общего состояния) — нарушение
**Где:** `core/librarian_core.py`, возможно `core/parser_db.py`

**Симптом:**
Открыт архив A (МГ). Добавлен архив B (другой). При открытии B
в UI видны сообщения из A.

**Воспроизведение:**
1. Открыть архив МГ (`#/a/Мастер%20Группа%20Макеевой%20Виолетты`)
2. Добавить второй архив (любой, можно копию МГ в другой папке)
3. Открыть второй архив
4. В «Последние сообщения» — сообщения из МГ, не из второго архива

**Корневая причина (предположительно):**
Один из вариантов:
- (a) `LibrarianCore` хранит `current_archive` как модульную глобаль,
  переключение не сбрасывает `parser_db` коннект
- (b) `librarian.db` создаётся один на все архивы (общий путь),
  индексы смешиваются
- (c) `ParserDB` кэшируется по пути, но кэш не инвалидируется при
  смене архива

**Ожидаемый фикс:**
Каждый архив = свой `ParserDB` + свой `LibrarianDB`. Никакого
`current_archive` — `archive_id` передаётся в каждый вызов явно.
Кэш инвалидируется при `remove_archive`.

**Регрессионный тест:** `test_archive_isolation_no_leak`

### BUG-003 — Поиск по нику находит 2 сообщения вместо ~40 000

**Severity:** major (критично для UX, но не ломает программу)
**Класс:** П6 (поиск по автору — отдельный режим) — частично
реализован, но UX непонятен
**Где:** `core/librarian_db.py` (`search()`), `static/index.html`

**Симптом:**
Ввод ника автора в строку поиска возвращает 2 сообщения. Ожидается
~40 000 (все сообщения этого автора).

**Воспроизведение:**
1. Открыть архив МГ
2. В строку поиска ввести ник автора
3. Результат: 2 сообщения (там, где ник упомянут в тексте)
4. Ожидается: либо все сообщения автора, либо подсказка «используйте
   фильтр Автор»

**Корневая причина:**
FTS5 ищет по тексту, не по автору. Ник автора в тексте его сообщений
не фигурирует. Фильтр «Автор» есть в adv-панели, но пользователь
не понимает разницы.

**Что сделано:**
- В чипах подсказка «по автору: …»
- В no-results ссылка «Искать по автору»

**Что НЕ сделано (нужно доделать):**
- Отдельная кнопка/переключатель «по тексту / по автору» в строке
  поиска, не в adv-панели
- Если ввод начинается с `@` — автоматически искать по автору
- Подсказка в placeholder: «Поиск по тексту. Для автора — начните
  с @»

**Регрессионный тест:** `test_search_by_author_at_prefix`

### BUG-004 — Клик на найденное сообщение → «не удалось определить chat_id»

**Severity:** critical (ломает навигацию)
**Класс:** П8 (навигация из поиска в ридер — на реальном архиве) — нарушение
**Где:** `static/index.html`, возможно `core/tools.py` (`get_message`)

**Симптом:**
После поиска клик на результат → «Загрузка…», затем ошибка
«Не удалось определить chat_id». Ридер не открывается.

**Воспроизведение:**
1. Открыть архив МГ
2. Ввести частое слово в поиск → получить результаты
3. Кликнуть на первый результат
4. Вместо ридера — ошибка

**Корневая причина (предположительно):**
UI-4 ридер ожидает `chat_id` в результате поиска или в URL. На
демо-архиве `chat_id` извлекается из `archive_passport.json`. На
реальном архиве МГ поле либо названо иначе, либо структура паспорта
отличается.

Дополнительная гипотеза: `chat_id` есть в `parser.db` (`chats` или
`cached_dialogs` таблица), но не пробрасывается в результат поиска.

**Ожидаемый фикс:**
1. `search()` возвращает `chat_id` для каждого результата (из
   `messages.chat_id` или join с `chats`)
2. UI при клике берёт `chat_id` из результата, не из паспорта
3. Если `chat_id` всё же нужен из паспорта — фолбэк на `0` или
   на первый чат из `chats` таблицы

**Регрессионный тест:** `test_search_result_opens_reader_real_archive`

### ARCH-004 — Облако тегов (из #хештегов в сообщениях)

**Severity:** enhancement
**Класс:** новая фича, не баг
**Источник:** запрос пользователя 30.07.2026 во время ревью
**Где:** `core/librarian_db.py` (build_index), `static/index.html` (UI)

**Симптом/пожелание:**
На главной архивов и в читальном зале хорошо бы показывать
облако тегов, если они есть в чате. Теги — это #хештеги в текстах
сообщений.

**Данные (проверено 30.07.2026 на архиве МГ):**
В `parser.db` **нет** отдельной таблицы тегов. Прогон регулярки
`#([a-zA-Zа-яА-Я0-9_]{2,30})` по `messages.text` дал:
- 114 уникальных тегов
- топ: #ответвиолетты (×1788), #qrbase (×332), #презрение (×98),
  #сравнение (×69), #проверкапроработки (×65), #отвержение (×54),
  #покинутость (×48), #qabase (×42), #травмаотвержения (×41), ...

То есть теги — содержательные (темы проработок, выпуски, методы),
не спам. В чате «Ландшафтный беспредел» тегов нет (обычный чат).

**Предлагаемая архитектура:**

1. **Индексация** (один раз при `build_index`):
   - В `librarian_db.build_index()` добавить регекс
     `#([a-zA-Zа-яА-Я0-9_]{2,30})` (unicode-aware)
   - Создать таблицу `tags(tag_norm TEXT, tag_orig TEXT,
     message_id INT, chat_id INT)` с индексом по `(tag_norm, chat_id)`
   - `tag_norm` — lowercase; `tag_orig` — как в тексте (для tooltip)

2. **API:**
   - `GET /api/archives/{id}/tags?limit=50` → топ-тегов архива
     с частотой
   - `GET /api/archives/{id}/chats/{chat_id}/tags?limit=50` →
     топ-тегов конкретного чата
   - В search-ответе для каждого сообщения — список его тегов
     (для отображения под текстом как кликабельные чипы)

3. **UI:**
   - На главной архивов — облако под каждой карточкой (топ-20)
     или общее облако архива при наведении
   - В читальном зале — отдельная панель «Теги чата» сверху,
     топ-30, размер шрифта пропорционален частоте
   - Клик на тег → фильтр поиска: `text MATCHES "#тег\b"`
   - В результатах поиска — теги сообщения показаны как чипы

**Подводные камни:**
- Регекс должен ловить `#тег,`, `#тег.`, `#тег)`, `#тег;` —
  то есть граница слова, а не конец строки
- CamelCase: `#QrBase` и `#qrbase` — один тег (нормализация),
  но оригинал показываем в tooltip
- Теги с цифрами (`#п3в31`) — содержательные (выпуски),
  не выкидывать
- Минимальная длина 2 символа (отсечь `#1`, `#!`)
- Для больших чатов (16 000+ сообщений) — индексация может
  занять 1-3 секунды, надо кешировать в librarian.db

**Вопросы к ревьюеру:**
1. Нормализовать ли `#QRBase` и `#qrbase` в один тег?
   (предложение: да, через lowercase, оригинал в tooltip)
2. Показывать ли тег только если он встречается ≥ N раз?
   (предложение: ≥ 3, чтобы не засорять облако редкими)
3. Стоит ли теги вынести в отдельный FTS-индекс для поиска
   «все сообщения с тегом X»? Или достаточно `LIKE '#X %'`?
4. В чатах без тегов (как «Ландшафтный беспредел») —
   скрывать панель или показывать «тегов нет»?

**Ожидаемая трудоёмкость:** 2-3 часа (индексация + API + UI)

### ARCH-005 — Чат-вью как в HTML-экспорте парсера + живая фильтрация

**Severity:** enhancement (сильное влияние на UX)
**Класс:** новая фича, не баг
**Источник:** запрос пользователя 30.07.2026, с приложенным примером
  `💚Ландшафтный беспредел_Дуплекс 222_2026-06-03_to_2026-07-03.html`
**Где:** `static/index.html` (reader view), `core/parser_db.py`
  (дерево ответов), `main.py` (WS-обработчики)

**Симптом/пожелание:**
Хочется, чтобы при открытии чата в Librarian он выглядел так же,
как в HTML-экспорте парсера — с тредами, аватарами, цитатами,
изображениями, транскрипциями. И чтобы тут же работали фильтры:
- «показать ветки с выбранным участником»
- «показать только сообщения выбранного участника»

**Эталон — HTML-экспорт парсера:**

Структура (классы CSS из примера):
- `.message.depth-N` — отступ 0/32/56/80/104/128 px по уровню
  треда (через `reply_to_msg_id`)
- `.msg-row` — flex: аватар + контент
- `.avatar` — кружок 36×36 с инициалом автора (одна буква)
- `.author` + `.date` — заголовок сообщения
- `.reply-badge` — «↪️ ответ» со ссылкой `#msg_<parent_id>`
- `.quote-preview` — кликабельный цитат-превью (обрезка 60 симв)
  с подсветкой оригинала при клике (1 сек, класс `highlight`)
- `.msg-text` — текст с `white-space: pre-wrap`,
  `word-break: break-word`, ссылки подсвечены
- `.msg-media` — ссылка на вложение (видео/файл)
- `.msg-img` — встроенное изображение (`<img>` тег)
- `.msg-stt` — транскрипция (STT), курсив, левая граница серая
- `.msg-imgdesc` — VLM-описание изображения, курсив, граница зелёная
- `.header` — sticky заголовок с title и количеством сообщений
- `.scroll-top` — фиксированная кнопка «наверх»
- Цветовая схема: `#0e1117` фон, `#FF9500` акцент, `#e7edf5` текст

**Данные в parser.db (проверено 30.07.2026):**
- `messages.reply_to_msg_id` — есть, для тредов
- `messages.username` — есть, для автора
- `messages.media_path` + `file_type` — есть (photo/video/file)
- `transcriptions.text` — есть, по `message_id`
- VLM-описаний в текущей схеме нет (нужно отдельное поле или таблица)

**В Мастер-Группе Макеевой:**
- 16 495 сообщений всего
- 16 436 с `reply_to_msg_id NOT NULL` (99,6% — ответы!)
- То есть треды — основная структура, без них читальный зал бесполезен

**Предлагаемая архитектура:**

1. **Backend:**
   - Новый WS-обработчик `chat_view`: на вход `archive_id`,
     `chat_id`, опционально `filters` (username, tag, date range)
   - Возвращает НЕ плоский список, а **дерево**: для каждого
     сообщения — `parent_id`, `depth`, список `children_ids`
   - Клиент строит DOM по дереву (отступы depth-0..5)
   - Для фильтра «только сообщения участника» — плоский список,
     без дерева (см. ниже режим А)
   - Для фильтра «ветки с участником» — серверная функция
     `branches_with_user(chat_id, username)` (см. ниже режим Б)

2. **Режимы фильтрации:**

   **А. «Только сообщения участника»** (простой)
   ```sql
   SELECT * FROM messages
   WHERE chat_id=? AND username=?
   ORDER BY date
   ```
   Плоский список, без тредовой структуры. Подходит для быстрого
   просмотра активности.

   **Б. «Ветки с участием участника»** (контекстный)
   - Найти все сообщения участника
   - Для каждого — подняться по `reply_to_msg_id` до корня
   - Опуститься по дереву — собрать все ответы (BFS, рекурсивно)
   - Показать как лес деревьев, сообщения участника подсвечены,
     остальные — серые
   - Алгоритм (Python, набросок):
   ```python
   def branches_with_user(db, chat_id, username):
       user_msgs = db.execute(
           "SELECT message_id FROM messages WHERE chat_id=? AND username=?",
           (chat_id, username)).fetchall()
       visited = set()
       for (mid,) in user_msgs:
           # вверх до корня
           cur = mid
           while cur and cur not in visited:
               visited.add(cur)
               row = db.execute(
                   "SELECT reply_to_msg_id FROM messages "
                   "WHERE chat_id=? AND message_id=?",
                   (chat_id, cur)).fetchone()
               cur = row[0] if row else None
           # вниз — все ответы (BFS)
           queue = [mid]
           while queue:
               parent = queue.pop(0)
               children = db.execute(
                   "SELECT message_id FROM messages "
                   "WHERE chat_id=? AND reply_to_msg_id=?",
                   (chat_id, parent)).fetchall()
               for (child,) in children:
                   if child not in visited:
                       visited.add(child)
                       queue.append(child)
       return visited
   ```

3. **UI:**
   - При открытии чата — переключатель режима:
     «Все сообщения» / «Только участник» / «Ветки участника»
   - Селектор участника — список из `chats` или autocomplete
   - В режиме «Все» — дерево с отступами depth-0..5, как в парсере
   - В режиме «Только участник» — плоский список, без отступов
   - В режиме «Ветки участника» — лес деревьев, чужие сообщения
     в `opacity: 0.4`
   - Живой режим: переключение не перезагружает страницу,
     только WS-запрос с новым фильтром

4. **Производительность:**
   - Для МГ (16 495 сообщений) режим Б может вернуть почти весь
     чат (т.к. 99,6% — ответы, и деревья сильно связаны)
   - Нужен лимит: например, не больше 500 сообщений в выдаче
     режима Б, иначе предлагать сузить по дате
   - Или лимит глубины BFS (не глубже 3 уровней от сообщения
     участника)

**Подводные камни:**
- `messages.message_id` (телеграм-айди) vs `messages.id` (rowid):
  в reply_to_msg_id хранится именно `message_id`. Проверить,
  что мы везде используем одно и то же поле.
- Циклы в `reply_to_msg_id` (сообщение отвечает на себя или на
  потомка) — теоретически возможны при экспорте битого чата.
  Нужен guard в BFS.
- Изображения — в `media_path` путь может быть относительным
  (от папки архива). Сервер должен отдавать их через
  `/api/archives/{id}/media/...` с правильным content-type.
- VLM-описаний сейчас нет в БД — нужно либо добавить колонку
  в `messages` (если парсер начнёт их сохранять), либо отдельную
  таблицу `image_descriptions(message_id, text, model)`.

**Вопросы к ревьюеру:**
1. Дерево строить на сервере или на клиенте? На сервере —
   меньше трафик, на клиенте — проще фильтры переключать.
   (предложение: сервер отдаёт плоский список с parent_id,
   клиент строит дерево)
2. Режим Б — лимит 500 сообщений справедлив? Или лимит по
   времени (например, ветки за последние 30 дней)?
3. Стоит ли кешировать `branches_with_user` по `(chat_id,
   username)` в librarian.db? Чат не меняется, можно один раз
   посчитать.
4. Имена `username` — это display name (как «elenaohapkina»)
   или Telegram @handle? Если второе, нужны отдельные имена
   для отображения (из `chats.metadata` или отдельной таблицы
   participants).

**Ожидаемая трудоёмкость:**
- Backend (WS handler + дерево + 2 режима фильтрации): 4-6 часов
- UI (копия парсерского чат-вью + селекторы фильтров): 1-2 дня
- Тесты на дерево и фильтры: 2-3 часа
- Итого: ~2 рабочих дня

До этого структура была «в голове» и расходилась между демо-архивами

## 1. Каноническая структура: Telegram-чат

```
output/ИмяЧата/                    ← корень архива Telegram-чата
├── telegram_archive.db            ← Каноническое имя DB парсера.
│                                    (Алиас для демо: parser.db)
├── archive_passport.json          ← Метаданные архива (опционально)
├── human/                         ← Выгрузки для людей
│   ├── ИмяЧата_full.docx          ← DOCX (с фильтрами парсера)
│   └── ИмяЧата_full.html          ← HTML (с фильтрами парсера)
├── llm/                           ← Выгрузки для LLM
│   ├── ИмяЧата_ai/                ← MD с ai_split=True
│   │   ├── post_0001.md
│   │   └── ...
│   ├── ИмяЧата_kb.md              ← MD базы знаний (ai_split=False)
│   └── ИмяЧата.json               ← JSON-экспорт
├── media/                         ← Исходные медиа
│   ├── files/
│   ├── photos/
│   └── videos/
└── transcripts/                   ← .md-транскрипции ТОЛЬКО видео
                                    ← Имена = stem видео (см. §3)
                                    ← 00_INDEX.md — опционально (см. §4)
```

### Что куда (правило деления human/ vs llm/) [поправлено 31.07.2026 по второму замечанию парсера]

| Папка | Форматы | Фильтры парсера | Потребитель |
|---|---|---|---|
| `human/` | DOCX, HTML | **применяются** (человек читает выборку) | пользователь |
| `llm/` | MD (split/kb), JSON | **не применяются** (корпус для LLM должен быть полным) | LLM / Librarian |

Это автоматически закрывает вопрос «есть ли смысл в фильтрах парсера»:
смысл есть, но только для `human/`. Для `llm/` выгружаем всегда полностью.

### Как это правило доходит до пользователя (важно)

**Нельзя молча игнорировать фильтр для MD/JSON.** Если пользователь
поставил «кроме Марии» и получил файл, в котором Мария есть, — это
тихая подстановка, ровно та дыра, которую закрыли в DOCX-экспорте,
только в новом костюме. Молчаливое нарушение явного указания
пользователя хуже, чем неполный корпус: неполноту он увидит, а тихую
подстановку — нет.

**Нельзя и блокировать панель фильтров при выборе MD/JSON-пресета.**
Пресеты только выставляют начальные галочки, пользователь свободно
доснимает и доставляет форматы. Выбрал «Полный архив», доставил MD —
фильтр снова с ним. Блокировка легко обходится и создаёт ложное
чувство контроля.

**Правильный механизм — видимое разделение:**

1. Фильтры доступны всегда, для всех форматов, без блокировок.
2. Перед стартом экспорта — окно подтверждения с явным текстом,
   например:
   > **Фильтр «кроме Марии» применится к:**
   > ✅ DOCX, HTML (выборка для человека)
   >
   > **MD и JSON выгрузятся целиком (корпус для LLM)** — фильтр на
   > них не действует. Если нужно отфильтровать MD/JSON — сделайте
   > отдельный прогон с этим фильтром.
3. Пользователь подтверждает или отменяет. Никаких сюрпризов после.

Деление `human/` + `llm/` само по себе это правило объясняет —
папка в пути файла уже подсказывает, что фильтр действовал или нет.
Окно подтверждения делает правило видимым **до** экспорта, а не после.

### Где транскрипции

Раньше транскрипции лежали в `media/videos/transcripts/`. Переносим
в `<archive>/transcripts/` — отдельная папка верхнего уровня. Причины:

1. Сразу видно, есть ли в архиве расшифровки.
2. Не смешиваются исходники (`media/`) и производные артефакты.
3. Единое правило для Telegram-чатов и не-Telegram курсов (см. §2).

### Что НЕ входит в transcripts/

- **Voice / video note** — расшифровка встраивается прямо в `messages.text`
  (в БД). Отдельного .md-файла нет и быть не должно. Librarian читает
  `text` из DB.
- **00_INDEX.md** — это не транскрипция, а оглавление (см. §4).

## 2. Каноническая структура: не-Telegram курс

У курсов своя структура папок (Урок1/, Урок2/, ...), которая имеет
смысл. Не ломаем её. Транскрипции складываем параллельным деревом:

```
Курс/
├── Урок1/
│   ├── lecture.mp4
│   ├── slides.pdf
│   └── notes.docx
├── Урок2/
│   └── lecture.mp4
└── transcripts/                   ← Зеркало структуры курса
    ├── Урок1/
    │   └── lecture.md             ← Имя = stem видео
    └── Урок2/
        └── lecture.md
```

**Почему параллельное дерево (вариант B):**
- Исходники не трогаем — транскрайбер пишет в `transcripts/`.
- Путь `transcripts/Урок3/lecture.md` сам по себе несёт контекст
  (Librarian видит `parent.name == "Урок3"`, без парсинга имени).
- Работает для любой вложенности через `pathlib.Path.rglob()`.
- Никакого «интеллектуального распознавания» — обычная файловая система.

Librarian обходит `transcripts/` рекурсивно, для каждого .md-файла:
- `relative_path` = путь относительно `transcripts/` → контекст
- `stem` (имя без расширения) → связь с исходным медиа

---

## 3. Имена транскрипций

**Правило:** имя .md-файла = stem исходного медиа.

| Медиа | Транскрипция |
|---|---|
| `voice_5084.ogg` | `voice_5084.md` |
| `video_lesson_3.mp4` | `video_lesson_3.md` |
| `lecture.mp4` (в `Урок1/`) | `transcripts/Урок1/lecture.md` |

**Stem** — имя файла без расширения. Это позволяет Librarian'у по
`media_path` из DB найти транскрипцию:
1. Взять `media_path = "media/videos/voice_5084.ogg"`.
2. Отрезать расширение → `voice_5084`.
3. Добавить `.md` → `voice_5084.md`.
4. Посмотреть в `transcripts/voice_5084.md`.

**Никаких метаданных в имени.** Никаких «транскрипция_видео_3_урок_7_выпуск_850.md».
Имя — машиночитаемая связь с медиафайлом. Оглавление — отдельно (§4).

Ранее имена транскрипций курса были вынужденно сложными (для построения
оглавления со списком выпусков). Это решение разделить две задачи:
- транскрипция = простая, машиночитаемая
- оглавление = отдельный файл, человеческая забота

## 4. 00_INDEX.md (и любые 00_*.md) — опциональный артефакт

**Кто создаёт:** пользователь (или LLM по запросу пользователя). Парсер
его не пишет, транскрайбер его не пишет, Librarian его не пишет. Это
человеческий артефакт.

**Зачем:** дерево даёт «где лежит», индекс даёт «о чём это и что важно».
Того, чего нет в файловой системе:
- темы уроков (папка `Урок3` не говорит, что урок про дренаж)
- заметки «вот тут полезно», «это устарело», «это ядро курса»
- таймстампы ключевых моментов
- связи между уроками («Урок 12 продолжает Урок 7»)

**Когда нужно:**
- планируешь работать с курсом через LLM-агента, и агенту нужен
  контекст сверх того, что есть в путях
- когда в чате есть выпускная структура (как в МГ с #п3в31 и т.п.)

**Когда НЕ нужно:**
- простое чтение без LLM-агента
- Librarian в штатном режиме (работает по дереву и DB)
- простой чат без сложной структуры

**Формат:** свободный Markdown, без жёсткой схемы. Пример:

```markdown
# Оглавление курса «Ландшафтный беспредел»

## Структура
- 20 уроков, каждый в папке `УрокNN/`
- В каждом: `lecture.mp4`, `slides.pdf`, иногда `notes.docx`
- Транскрипции: `transcripts/УрокNN/lecture.md`

## Уроки
1. Урок1 — Введение. Есть видео, есть слайды.
2. Урок2 — Базовые понятия дренажа. Только аудио.
...

## Заметки
- Урок 7 технически устарел, можно пропустить.
- Уроки 12-15 — ядро курса, читать внимательно.
```

**Как Librarian с ним обращается:**
- Если файл есть — Librarian **может** (не обязан) подсунуть его в
  контекст при поиске по этому курсу.
- Если файла нет — работает как обычно, по дереву и DB.
- Текущая логика `_load_index_transcripts()` уже это делает: если
  находит `00_*.md`, использует как подсказку; если нет — игнорирует.

**Не является артефактом архива:** не требуется для работы Librarian,
не валидируется при детекте архива, не входит в паспорт.

## 5. DB-контракт: метаданные чата

Метаданные чата Librarian берёт из таблицы `chats` архивной DB.

| Поле | Откуда брать | Сейчас (31.07.2026) | Потом |
|---|---|---|---|
| `title`, `type`, `linked_chat_id` | `chats` | ✅ есть | ✅ |
| `participants_count` | `chats` | ❌ нет, fallback `COUNT(DISTINCT user_id)` | ✅ будет в `chats` |
| `has_comments` | `chats` | ❌ NULL | ✅ будет в `chats` |
| `is_linked_discussion` | `chats` | ❌ NULL | ✅ будет в `chats` |

`DBManager.get_chat_info()` использовать можно, но в документации
явно помечаем: «`participants_count` сейчас — это число писавших за
период, а не участников чата; настоящее значение приедет в `chats`
позже, когда парсер начнёт их сохранять».

### Что НЕ читаем

`cached_dialogs` в архивной базе **не читаем ни сейчас, ни потом**.

Пояснение: `cached_dialogs` — это кэш списка чатов, который пишет
модуль `features/chats/ui.py` в отдельную базу `dialogs_cache.db`.
Схема таблицы применяется ко всем базам подряд (поэтому `cached_dialogs`
есть в `telegram_archive.db`), но парсер её не пишет — это не его данные.
В реальных архивах таблица пуста **штатно**, это не баг парсера и не
мёртвая фича. Librarian'у эти данные не нужны.

### Планируемое изменение контракта (в Parser)

Когда парсер начнёт сохранять `participants_count`, `has_comments`,
`is_linked_discussion` — они приедут в `chats`. Контракт Librarian
не меняется: те же поля в той же таблице. Только fallback для
`participants_count` уходит.
