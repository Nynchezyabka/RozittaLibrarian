## 📋 О проекте

**Название:** Rozitta Librarian
**Что это:** Веб-приложение для поиска и чтения архивов Telegram, скачанных
[Rozitta Parser](https://github.com/Nynchezyabka/RozittaLibrarian).
**Скелет:** FastAPI + одна HTML-страница + WebSocket, порт по умолчанию 8011
(перекрывается переменной окружения `LIBRARIAN_PORT`).
**Слой без LLM («Читальный зал») — цель этапа 1:** открыть программу →
выбрать архив → искать по FTS5 → читать посты и комментарии →
пользоваться без единой настройки модели.

---

## 🧱 Технологический стек

- **Python 3.10+**
- **FastAPI + Uvicorn** — HTTP + WebSocket на одном порту
- **SQLite3** — два подключения: `parser.db` (read-only) и собственный
  `librarian.db` (FTS5, токенизатор `unicode61`)
- **webbrowser + threading** — авто-открытие браузера после старта сервера
  (демон-поток, задержка 1.5 c, отключается флагом `--no-browser`)
- **Vanilla JS** в браузере — без сборщиков, без фреймворков; один
  `static/index.html`, генерируется из макета через `scripts/build_index_html.py`

## 🏛️ Архитектура в двух словах

```
пользователь ─→ браузер ─→ WebSocket /ws
                              │
                              ▼
                          main.py (FastAPI)
                              │
                              ▼
                       LibrarianCore (фасад)
                       ┌──────┴──────┐
                       ▼             ▼
                   ParserDB       LibrarianDB
                  (read-only)     (librarian.db + FTS5)
                       │             │
                       └──┬──────────┘
                          ▼
                      tools.py
            ┌────────┬────────┬────────┬────────┬────────┐
            ▼        ▼        ▼        ▼        ▼        ▼
        search() read_post() get_message() stats() whats_new() list_shelves()
```

- Браузер общается с сервером **только через WebSocket** на `/ws`.
  Сообщения вида `{"op": "...", "archive_id": "...", "args": {...}}`.
- HTTP-эндпоинты (`/api/archives`, `/api/archives/{id}/card` и т.д.) —
  для лёгкой интеграции и проверки без WS.
- Долгие SQL-операции уходят в threadpool через `asyncio.to_thread`,
  чтобы event loop мог параллельно слать `log`-сообщения в браузер.

## 🔌 WebSocket-операции (текущий список)

| `op`              | Назначение                                                       |
|-------------------|------------------------------------------------------------------|
| `list_archives`   | Карточки архивов из `output/`                                    |
| `scan_archives`   | Принудительно пересканировать `output/`                          |
| `open_archive`    | Карточка + полный паспорт; попутно строит FTS, если устарел      |
| `top_terms`       | Топ-термины архива (для чипов-примеров)                          |
| `search`          | FTS5-поиск с фильтрами (author, date_from/to, source/shelf)      |
| `get_message`     | UI-4 ридер: пост + транскрипция + комментарии + соседи + t.me    |
| `read_post`       | То же, но без соседей и t.me (оставлен для совместимости)        |
| `stats`           | `kind=overview` (счётчики, диапазон, топ-авторов) или `authors` |
| `whats_new`       | Лента новых сообщений с `since`                                  |
| `list_shelves`    | Полки из паспорта архива                                         |

Каждая операция возвращает `{"type": "result", "op": ..., "data": ...}`;
параллельно шлёт `{"type": "log", "level": "info|success|warning|error", "message": ...}`.

## 🧊 Ключевые правила — НЕ нарушать

1. **База Parser — только чтение.** `parser.db` открывается через
   `file:...?mode=ro` + `PRAGMA query_only = ON`. Ни одной записи.
2. **Своя база `librarian.db`** лежит рядом с `parser.db`. FTS5
   (токенизатор `unicode61`) над `messages.text` + `transcriptions.text`.
   При изменении схемы поднимаем `INDEX_VERSION` в `librarian_db.py`.

2а. **Транскрипты приходят ИЗ ПАПКИ, не только из базы.** Таблица
   `transcriptions` в `parser.db` может быть пуста — Transcriber пишет
   файлы `.md`, а не строки в базу (в архиве Мастер-группы она пуста,
   и 46 расшифровок при индексации теряются). Второй источник индекса:
   файлы расшифровок из папки архива, связь «пост → файл» держит
   `00_Индекс.md` от `make_index.py`, привязка — по ведущему номеру
   поста в имени (`В14_п109_…` и `109_…` равноценны, переименование —
   косметика для человека). Архив может быть частично готов (видео есть,
   расшифровки нет) — это нормально, показывать честно, конвейер из трёх
   программ не строить. Готовый разбор индекса: `eval_fts.py`,
   функция `load_index_transcripts()`.
3. **Чипы — динамические, в библиотекаре, не в парсере.**
   `chips` больше нет в `archive_passport.json`. Чипы вычисляются через
   `LibrarianDB.top_terms(limit=8, min_len=6)` из FTS5-словаря (`fts5vocab`)
   при открытии архива. Простые средние слова — этого достаточно,
   никакой интерактивности.
4. **Префиксные формы + ОБРЕЗКА ОКОНЧАНИЯ В ЗАПРОСЕ.** Одной звёздочки
   мало: префикс ищет по форме из вопроса, поэтому `зависти*` НЕ находит
   «зависть» — поиск молча вернёт пустоту. Слово из запроса надо сначала
   укоротить: снять частое русское окончание, затем обрезать до ~6 букв
   (`зависти` → `завист*`, `сравнения` → `сравне*`). Замер 28.07:
   62% → 88% на эталонном наборе. Приёмочный тест: запрос «зависти»
   обязан находить пост про зависть.

4а. **Квоты по типу источника — обязательны.** `search()` НЕ возвращает
   глобальный топ. BM25 нормирует по длине, поэтому длинная расшифровка
   всегда проигрывает короткой реплике; в реальном архиве 16 177
   комментариев против 102 документов автора, и при общей выдаче материал
   автора не попадает в топ-10 НИ РАЗУ (замер 28.07: 7/7 на пуле автора
   против 0/7 на общем при одинаковом запросе). Поэтому: топ-N среди
   `is_comment = 0` ПЛЮС топ-N среди `is_comment = 1`, слить, каждый
   результат помечен своим типом. Комментарии не выкидывать — часть
   ответов (разборы автора в обсуждениях, разметка хештегами) живёт
   только там. На демо-архивах эффект не виден: там 18 и 11 сообщений.

4б. **Узкая выдача лучше широкой.** Замер: при k = 10 результат
   становится статистически неотличим от случайного, при k = 3–5 —
   значим (p < 0.005). Для агента (этап 2) отдавать 3–5 на тип
   источника, не 20.
5. **5 инструментов не знают про LLM** — тестируются без модели. Их же
   использует UI (этап 1) и (будущий) MCP-выход (этап 6).
6. **Ответы Librarian (этап 2+) никогда не попадают в поисковый индекс** —
   иначе он начнёт цитировать сам себя.
7. **`static/index.html` НЕ правится вручную.** Источник — UI-макет, сборка
   через `python3 scripts/build_index_html.py`. Правки JS — в макете или в
   шаблонах сборщика, потом пересобираем.
8. **Перед коммитом:** `pytest tests/ -v` (22 теста) и
   `python3 scripts/test_ui_ws.py` (11 smoke-тестов) должны быть зелёными.

## 📏 Замеры качества поиска (28.07.2026)

Инструмент: `eval_fts.py` + `eval_questions.yaml` (23 вопроса с размеченными
источниками). Метрика — recall@k, контроль — среднее по 1000 случайных
выдач, значимость — перестановочный p-value.

| Что установлено | Число |
|---|---|
| Поиск по терминам работает | 7/8 при случайных 0/8 |
| Вопрос живым языком, без модели | 2/7, p = 0.19 — неотличим от случайного |
| То же + переформулировка моделью (deepseek, вслепую) | 5/7, p = 0.000 |
| Потолок при идеальных терминах | 7/7 |
| Общая выдача вместо квот по типу | 0/7 |

Выводы: эмбеддинги сняты с рассмотрения; агентный цикл — несущая
конструкция, а не улучшение; квоты и обрезка окончаний обязательны.
Подробности и условия пересмотра — `librarian_статус.md`.

### 🔒 Правила профилактики (нарушать НЕЛЬЗЯ)

**П1. Идемпотентность `add_archive` и `remove_archive`.**
Любая операция с реестром архивов обязана быть идемпотентной.
`add_archive(id)` — если `registry.has(id)`, вернуть существующую карточку,
не создавать новую. `remove_archive(id)` — если `registry.has(id)` ложно,
считать успехом (уже удалено). `refresh_discovery()` — добавлять только
то, чего ещё нет в реестре, и **никогда** не поднимать удалённое вручную.

**П2. Нормализация id архива.**
Id архива — это имя папки, оно может содержать пробелы, кириллицу,
длинные имена. Для URL использовать slug-форму (`slugify(id)`),
для отображения — оригинал. Любой поиск в `registry` обязан идти
через ту же нормализацию, что и при `add`. Тест на id с пробелом и
кириллицей — обязателен.

**П3. Карточка архива = счётчик из БД, не из паспорта.**
`archive_card.to_dict()` берёт `count_messages()` из `parser_db`,
а не `messages_count` из `archive_passport.json`. Паспорт может
отсутствовать или быть устаревшим. UI показывает то, что считает
бэкенд. Тест: карточка с пустым паспортом показывает ненулевой
счётчик, если в БД есть сообщения.

**П4. Изоляция архивов — никакого общего состояния.**
Каждый архив = свой `ParserDB` (read-only коннект) + свой `LibrarianDB`
(свой `librarian.db` рядом с `parser.db`). Никаких модульных глобалов,
никакого кэша «последний открытый архив». Если открыт архив A, а потом
архив B — все операции обязаны идти в B, обращения в A — ошибка.
Тест: открыть A, открыть B, запросить сообщение из A → должно вернуть
ошибку «archive not opened», не данные A. **(Сейчас нарушено — см. KNOWN_ISSUES.md #2.)**

**П5. Сортировка последних сообщений.**
«Последние сообщения» = `ORDER BY date DESC LIMIT N`. Никаких
`ORDER BY ASC + reversed()`. Любая такая конструкция в коде — баг.
Тест: создать 3 сообщения с датами t1 < t2 < t3, вызвать `whats_new()`,
ожидать `[t3, t2, t1]`.

**П6. Поиск по автору — отдельный режим.**
FTS ищет по тексту. Ник автора в тексте обычно не упоминается.
«Поиск по нику» = `WHERE author LIKE '%nick%'` (или точное
равенство), не FTS. UI обязан различать два режима и не путать
пользователя. Тест: автор с 40 000 сообщений, поиск по нику →
должен вернуть ≥ 90% его сообщений или явную ошибку «слишком много
результатов, уточните».

**П7. `top_terms` — порог doc_freq обязателен.**
Чипы/подсказки берутся из `fts5vocab`, но с порогом: `doc_freq ≥ 5`,
длина слова 6–20, стоп-список (имена, местоимения, междометия).
Без порога в топ попадают единичные слова — они бесполезны. Если
после фильтров пусто — fallback на топ без порога, но это сигнал,
что архив странный (мало данных или очень узкая тема).

**П8. Навигация из поиска в ридер — на реальном архиве.**
UI-4 ридер (`get_message`) обязан открываться из результата поиска
на **реальном** архиве, не только на демо. Если `chat_id` не
извлекается — это баг, не fallback. Тест на реальной БД: открыть
поиск, кликнуть на первый результат, ридер должен показать пост.
**(Сейчас нарушено — см. KNOWN_ISSUES.md #4.)**

**П9. Транскрипции — из всех источников.**
Три источника расшифровок, индексируем все:
  (a) `transcriptions` таблица в `parser.db` (если Transcriber писал в БД),
  (b) `.md` файлы, на которые ссылается `00_Индекс.md`,
  (c) `.md` файлы во вложенных папках архива (рекурсивный обход).
Любой источник может быть пустым — это нормально. Тест: архив,
где (a) пусто, но (c) есть → расшифровки в индексе.

**П10. Идемпотентность patch-скриптов — маркер первым.**
В `apply_block(text, old, new, marker)` проверка маркера обязана
быть **первой**, до `old in text`. NEW-блок часто включает OLD
(как подстроку), поэтому без проверки маркера второй запуск
сопоставит OLD внутри NEW и применит патч повторно → дублирование.

**П11. Демо-архив недостаточен для регрессии.**
Демо-архив (18+11 сообщений) хорош для smoke. Любой баг, зависящий
от масштаба (FTS ranking, BM25, квоты, top_terms), на демо не
воспроизводится. Регрессионный тест обязан работать на расширенном
демо (≥ 100 сообщений + расшифровки + комментарии) —
`scripts/make_demo_archive.py` уже создаёт такой.

**П12. Реальный архив как часть CI — обязателен.**
Хотя бы один smoke-тест на реальном архиве МГ (с реальным
`telegram_archive.db`) — обязателен перед коммитом. Если реальный
архив недоступен на CI — писать тест, который SKIP'ается без него,
но НЕ удалять его. Иначе мы получаем ровно ситуацию 30.07:
22 unit + 11 WS зелёные, реальный архив не работает.

**П13. UI/бэкенд контракт — счётчики совпадают.**
Если бэкенд возвращает `count_messages()=16495`, UI обязан показать
«16 495 сообщений», не 0 и не «нет данных». Любое расхождение —
баг либо в API, либо в UI. Тест: сравнить `count_messages()` из
`/api/archives/{id}/inspect` с тем, что показывает карточка на главной.

**П14. Патчи — порядок применения.**
Патчи применяются в алфавитном порядке имён файлов. Если патч B
зависит от патча A — имя B должно идти после A. Между
независимыми патчами порядок не важен. Если сомневаешься —
указывай зависимость в docstring патча: «Требует: patch_X.py применён».

**П15. Документация — синхронно с кодом.**
`CLAUDE.md`, `librarian_статус.md`, `librarian_рабочий_план.md` —
обновляются в том же коммите, что и код. Если в коде появилось
новое правило (например, П4 выше), оно обязано попасть в
`CLAUDE.md` этого же коммита. Иначе следующий заход начинается
с расхождения между документом и кодом — это и было 28.07,
когда `CLAUDE.md` остался от Rozitta Parser.

**П16. Баг → регрессионный тест — в тот же коммит.**
Любой исправленный баг обязан получить регрессионный тест в
`tests/test_tools.py` или `scripts/test_ui_ws.py` в том же
коммите, что и фикс. Имя теста — `test_<bug-id>_<short-description>`.
Без теста баг вернётся — это случалось с порядком сообщений и
идемпотентностью `add_archive`.

### 🔬 Процедура: «тест на реальном архиве перед коммитом»

Перед коммитом любых изменений, которые трогают поиск, индексацию
или отображение архивов, выполнить (на машине с доступом к реальному
архиву МГ):

1. `pytest tests/ -v` — все юнит-тесты зелёные
2. `python3 scripts/test_ui_ws.py` — все WS smoke-тесты зелёные
3. Поднять сервер, открыть архив МГ в браузере:
   - На главной: счётчик сообщений ≠ 0 и совпадает с `/inspect`
   - Внутри архива: «Последние сообщения» показывают свежие,
     не самые старые
   - Поиск по частому слову — возвращает > 1 результата
   - Поиск по нику автора — возвращает его сообщения (через
     фильтр «Автор», не через текстовый поиск)
   - Чипы — осмысленные слова, не мусор
   - Клик на результат поиска — ридер открывается, показывает
     пост (не «chat_id не определён»)
4. Открыть второй архив — данные не смешиваются с МГ
5. Удалить архив — карточка исчезает, реестр не содержит

Если любой пункт не проходит — коммит блокируется.

### 📋 Когда раздел обновлять

- **Новый баг найден и исправлен** → добавить строку в таблицу
  + правило (если баг нового класса) + регрессионный тест.
- **Баг нового класса** → правило с префиксом П<номер>.
- **Баг известного класса** → просто строка в таблицу, со ссылкой
  на уже существующее правило.
- **Раз в квартал** — ревизия: убрать дублирующиеся правила,
  проверить, что все ещё актуальны.
