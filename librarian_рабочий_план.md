Отвечает на вопрос **«что делать дальше»**. Три файла проекта, у каждого
куска ровно один дом:

появилось одно и то же — удалить в одном и поставить ссылку.

## 1. Что это за программа (один абзац)

Librarian отвечает на вопросы по архиву, скачанному Rozitta Parser, и
**каждое утверждение в ответе подкрепляет ссылкой на конкретный пост**,
которую можно кликнуть и проверить. Внутри: модель (любая — локальная
или облачная) в цикле сама ищет по архиву полнотекстовым поиском SQLite,
читает найденное и пишет ответ; отдельный код без ИИ («Верификатор»)
после этого проверяет, что все ссылки настоящие. Если модели нет вообще —
программа всё равно полезна как быстрый поиск по архиву («читальный зал»).

## 2. Решения, которые уже приняты — НЕ пересматривать в процессе

1. **Поиск — FTS5 + агентный цикл, без векторной базы.** Подтверждено
   замером 28.07.2026 (см. `librarian_статус.md`). Эмбеддинги СНЯТЫ
   с рассмотрения, не отложены. Условие возврата одно и конкретное:
   если живой агентный цикл на этапе 2 даст на эталонном наборе
   заметно меньше 5/7.
2. **База Parser — только чтение.** Всё своё Librarian пишет в отдельный
   `librarian.db`.
3. **Модель — сменная деталь** (Ollama + любой OpenAI-совместимый API),
   не фундамент. Программа обязана быть полезной даже без модели.
4. **Верификатор без LLM.** Проверка ссылок — детерминированный код.
5. **Ответы Librarian никогда не попадают в поисковый индекс** (иначе он
   начнёт цитировать сам себя).
6. **Один процесс, один порт (8011), веб-интерфейс** — скелет как у
   Transcriber.
7. **Никакой автозагрузки моделей** — только честный статус «найдено /
   не найдено».

Если посреди разработки захочется «а может всё-таки векторы / может
дообучить / может бот в телеге» — это записано в разделе «Вне рамок»
исходного документа. Не сейчас.

## 3. Как это работает на пальцах (сквозной пример)

Вопрос: «Как прорабатывается обесценивание?»

```
Пользователь → UI
UI → Оркестратор: собрать промпт (режим + паспорт архива + блокнот)
Модель:  search("обесценива")        → 14 сниппетов
Модель:  read_post(122)              → полный текст
Модель:  read_post(127)              → полный текст
Модель:  финальный ответ со ссылками [пост 122], [пост 127]
Верификатор (код): пост 122 есть ✓, пост 127 есть ✓,
                   цитата №2 в тексте не найдена ⚠
UI: ответ с зелёными/жёлтыми пометками + панель «как я искал»
```

Всё, что делает модель — вызывает 5 инструментов и пишет текст.
Весь остальной интеллект — обычный код.

## 4. Пять инструментов (сердце программы)

| Инструмент | Что делает | Возвращает |
|---|---|---|
| `search(query, filters?)` | FTS5-поиск; слово из запроса ОБРЕЗАЕТСЯ до основы, потом `*`; выдача с КВОТАМИ по типу источника | 3–5 сниппетов на тип, ≤ 300 симв., с `message_id` и `is_comment` |
| `read_post(post_id, ...)` | Полный пост + комментарии + транскрипция, с пагинацией | текст со связями |
| `stats(kind, params?)` | Готовые числа: счётчики, динамика, авторы | только арифметика, никаких «смыслов» |
| `whats_new(since?)` | Что появилось после отметки | список нового |
| `list_shelves()` | Полки архива из паспорта | типы, описания, периоды |

Ключевое правило: инструменты **не знают про LLM**, тестируются юнит-
тестами без модели, и их же использует строка поиска в UI и MCP-выход.

## 5. Порядок работ

Каждый этап заканчивается работающей программой, а не «заделом».
Здесь — только состав этапов; отметки «сделано / в работе / застряло»
живут в `librarian_статус.md`, этот файл ими не засоряем.

### Этап 1 — «Читальный зал» (БЕЗ LLM) ← ТЕКУЩИЙ

Результат: открываешь программу → выбираешь архив → ищешь по нему
и читаешь посты. Уже полезно, уже можно показать людям.

Этап 1 разбит на две волны: **инструменты** (backend, задачи 1–5) и
**UI** (задачи 6–8). UI-волна оформлена как UI-1..UI-7 в
`librarian_ui_спецификация_этап1.md` §10; отметки «сделано / в работе»
живут в `librarian_статус.md`.

Задачи по порядку:
1. Каркас проекта: FastAPI + одна страница + WebSocket (скопировать
   скелет Transcriber). ✅
2. Подключение архива: найти папки в `output/`, прочитать
   `archive_passport.json`, показать карточки архивов. ✅
3. Чтение базы Parser (read-only): открыть SQLite, проверить
   `PRAGMA user_version` (схемы v1/v2), достать messages/chats/
   transcriptions. ✅
4. `librarian.db`: создать, построить FTS5-индекс поверх
   messages.text + transcriptions.text (токенизатор unicode61).
   Версия схемы индекса — в `INDEX_VERSION` (`core/librarian_db.py`).
   Текущая: 2 (`is_comment`, `post_message_id`). ✅
5. Инструмент `search()` + юнит-тесты на своём архиве. ✅
6. Инструменты `read_post()` и `get_message()` с пагинацией + тесты.
   `get_message` — расширенная версия для UI-4: пост + транскрипция +
   комментарии + соседи + ссылка t.me. ✅
7. UI-волна (см. спецификацию §10): экраны 1–4 + Rozitta-подсказки +
   dev-панель. **UI-1, UI-2, UI-3, UI-4 — готовы.** UI-5..UI-7
   (статистика, что нового, настройки) — следующий заход.
8. `stats()`, `whats_new()`, `list_shelves()` + тесты. ✅
   (инструменты готовы; UI-обвязка для `stats` и `whats_new` — UI-5/UI-6)

**Динамические чипы (решение по ходу, 2026-07-28).** Чипы-примеры
на карточке архива **больше не хранятся в `archive_passport.json`** —
парсер их не производит, и хранить их в архиве бессмысленно. Вместо
этого чипы вычисляются библиотекарем на лету: `LibrarianDB.top_terms()`
читает FTS5-словарь (`fts5vocab`) и возвращает топ-`N` слов длиной ≥ 6.
Простые средние слова — без интерактивности, без топ-терминов «по
значимости». См. CLAUDE.md §«Ключевые правила» п. 3.

### Этап 2 — Диалог с моделью

LLM-слой (Ollama + OpenAI-совместимый API, кнопка «Проверить»),
оркестратор (цикл ≤ 12 шагов, лимиты токенов/времени), экран «Диалог»
с live-логом шагов.

### Этап 3 — Верификатор

Извлечь ссылки регэкспом → проверить существование источников и цитаты →
разметка в UI (✓ / ⚠ / без источника).

### Этап 4 — Режимы и память

Классификатор режима (правила → дешёвый LLM-вызов → дефолт), три режима
(Архивариус / Консультант / Свободный), история сессий, блокнот корпуса
(заметки только с одобрения кнопкой).

### Этап 5 — Стенд качества

10–15 эталонных вопросов + 3 ловушки «про отсутствующее»; прогон модели
→ отчёт: % подтверждённых ссылок × токены × время × стоимость.

### Этап 6 — MCP-выход

Те же 5 инструментов наружу для Claude Desktop и других клиентов;
переключатель «разрешить внешние подключения», по умолчанию выключен.

## 6. Что сознательно откладываем (после MVP, отдельными решениями)

Маршрутизация двух моделей · вотчер Telegram · конвертер книг PDF/EPUB ·
Telegram-бот · многопользовательность · ранговое слияние выдач.

**Эмбеддинги и реранкер — сняты с рассмотрения** (не отложены).
Замер 28.07.2026: простая модель (deepseek), не видевшая корпуса,
переформулирует вопрос и выводит поиск из зоны случайности — 5/7 при
p = 0.000 против 2/7 при p = 0.19 у сырого вопроса. Потолок 7/7
закрывается настройкой промпта и вторым заходом агента, не векторами.

## 7. Известные риски (уже с ответами)

- Слабые модели ломают формат вызова инструментов → одно авто-исправление,
  потом честная ошибка.
- FTS5 без стемминга → **обязательна обрезка слова В ЗАПРОСЕ**: `зависти*`
  не находит «зависть», поиск молча вернёт пустоту. Снять окончание,
  обрезать до ~6 букв. Прежняя формулировка «префиксы покрывают ~90%»
  была неверна и проверена замером (62% → 88% после обрезки).
  Чередования («искать/ищу») лечим синонимами в промпте; лемматизация —
  потом, опционально.
- Материал автора тонет под комментариями (16 177 против 102 в архиве МГ)
  → квоты по типу источника в `search()`, иначе строгий зачёт 0/7.
- Транскрипции могут отсутствовать в `parser.db` (их пишет Transcriber
  файлами) → второй источник индекса: файлы по `00_Индекс.md`.
- Агент, склеивающий термины в раздельные запросы, ухудшает выдачу
  (2/7 против 5/7): равный вес мусорным словам. Термины склеивать
  в ОДИН OR-запрос — BM25 сам поднимет документ, совпавший с несколькими.
- Ответ идёт 5–15 секунд → показываем live-лог шагов вместо спиннера.
- Большие обсуждения не влезают в контекст → пагинация read_post +
  сжатие старых шагов до одной строки.
