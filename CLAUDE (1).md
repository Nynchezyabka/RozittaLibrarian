## 🎯 Основная функциональность

1. **Подключение архива** 🔜 — автопоиск папок в `output/`, чтение `archive_passport.json`
2. **Полнотекстовый поиск (FTS5)** 🔜 — по `messages.text` + `transcriptions.text`
3. **Просмотр поста** 🔜 — полный текст + комментарии + транскрипция, с подсветкой
4. **Экран «Поиск» без ИИ** 🔜 — «читальный зал», работает вообще без модели
5. **LLM-слой** 🔜 — Ollama + любой OpenAI-совместимый API (BYOM)
6. **Агентный цикл** 🔜 — модель сама делает серию поисков и читает найденное
7. **Верификатор** 🔜 — детерминированная проверка ссылок БЕЗ участия LLM
8. **Режимы** 🔜 — Архивариус / Консультант / Свободный + типы задач
9. **История и блокнот корпуса** 🔜 — память с плашками актуальности
10. **Стенд качества** 🔜 — сравнение моделей кнопкой, а не на глаз
11. **MCP-выход** 🔜 — те же инструменты наружу, по умолчанию выключен

## 🛠️ Технологический стек

- **Python 3.10+**
- **FastAPI** — HTTP + WebSocket, один процесс, порт 8011
- **SQLite3** — база Parser (read-only) + `librarian.db` (read-write)
- **FTS5** — встроенный полнотекстовый поиск SQLite, токенизатор `unicode61`
- **httpx** — вызовы LLM-провайдеров (OpenAI-совместимый HTTP, Ollama)
- **Vanilla JS + одна HTML-страница** — по скелету Transcriber, без фреймворков

**Чего в стеке НЕТ и не должно появиться в MVP:**
эмбеддинги · векторные базы (FAISS, Chroma, Qdrant) · torch · sentence-transformers ·
LangChain / LlamaIndex · Node.js · GPU-зависимости у самого Librarian.

## 🧭 Принятые решения (НЕ пересматривать в процессе)

| # | Решение | Почему |
|---|---------|--------|
| Р1 | Поиск — **FTS5 + агентный цикл**, без векторной базы | Устаревающий индекс на обновляемом архиве; необъяснимые «похожести» против проверяемости; корпус уже структурирован парсером |
| Р2 | База Parser — **только чтение**, никогда не запись | Librarian не должен портить данные другого продукта |
| Р3 | Модель — **сменная деталь**, не фундамент | BYOM; программа обязана быть полезной вообще без модели |
| Р4 | Верификатор — **без LLM** | «Кто сторожит сторожей»; работает одинаково при любой модели |
| Р5 | Ответы Librarian **никогда не попадают в FTS-индекс** | Иначе агент начнёт цитировать собственные ответы как источники |
| Р6 | Декомпозиция задач — **детерминированные рецепты**, не свободное LLM-планирование | Дешёвые модели не умеют планировать; рецепт можно показать пользователю заранее |
| Р7 | **Никакой автозагрузки моделей** | Ollama и ключи — забота пользователя; Librarian только честно показывает статус |

Если по ходу работы пришлось отступить от Р1–Р7 — это записывается в
`librarian_статус.md`, раздел «Решения, принятые по ходу», и правится
спецификация. Молча отступать нельзя.

## 🗄️ Схема базы `librarian.db`

Своя база, рядом с программой. Базу Parser не трогаем (Р2).

```sql
-- проекты: разные рабочие контексты поверх одних архивов
CREATE TABLE projects (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    archive_ids TEXT,              -- JSON
    shelf_selection_json TEXT,
    default_mode TEXT,
    default_model TEXT,
    context_note TEXT,             -- «что я здесь делаю», идёт в промпт Консультанта
    created_at TEXT
);

-- история диалогов: НИЧЕГО не удаляется автоматически
CREATE TABLE sessions (
    id INTEGER PRIMARY KEY,
    archive_id TEXT, started_at TEXT, title TEXT
);
CREATE TABLE turns (
    id INTEGER PRIMARY KEY,
    session_id INTEGER,
    role TEXT,                     -- user | assistant | tool
    content TEXT,
    tool_calls_json TEXT,          -- лог шагов — первоклассная сущность
    archive_watermark TEXT,        -- состояние архива на момент ответа
    created_at TEXT
);

-- блокнот корпуса: пишется ТОЛЬКО с одобрения пользователя
CREATE TABLE corpus_notes (
    id INTEGER PRIMARY KEY,
    archive_id TEXT, note TEXT, source TEXT,
    created_at TEXT, approved INTEGER DEFAULT 0
);

-- стенд качества
CREATE TABLE eval_questions (id INTEGER PRIMARY KEY, question TEXT, expected_sources TEXT, is_trap INTEGER);
CREATE TABLE eval_runs (id INTEGER PRIMARY KEY, model TEXT, run_at TEXT, report_json TEXT);

CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT);
```

**FTS5-индекс** — виртуальная таблица поверх `messages.text` + `transcriptions.text`,
токенизатор `unicode61`, морфология через префиксные запросы. Строится при первом
открытии архива, обновляется по `whats_new()`.

**Принцип:** всё, что можно вычислить из базы Parser — вычисляется, а не хранится
(кроме FTS-индекса, который дорого строить на лету).

## 🧷 ПРАВИЛА КОДИРОВАНИЯ (строго соблюдать)

### 1. База Parser — только чтение

```python
# ✅ ПРАВИЛЬНО:
conn = sqlite3.connect(f"file:{parser_db_path}?mode=ro", uri=True)

# ❌ ЗАПРЕЩЕНО — любой INSERT / UPDATE / DELETE / CREATE в базе Parser.
# Своё пишем ТОЛЬКО в librarian.db.
```

### 2. Инструменты не знают про LLM

```python
# ✅ ПРАВИЛЬНО — чистая функция, тестируется без модели:
def search(query: str, filters: dict | None = None) -> list[dict]: ...

# ❌ ЗАПРЕЩЕНО — импортировать agent/llm.py внутри core/tools/
```

Каждый инструмент обязан иметь юнит-тест, который проходит **без единого
вызова модели**. Если тест невозможен без LLM — инструмент спроектирован неверно.

### 3. Производные данные — НИКОГДА в FTS-индекс

```python
# ❌ ЗАПРЕЩЕНО индексировать: turns.content, ответы модели, сводки сессий.
# Поиск по ним — только через экран «История», отдельным индексом.
# Иначе агент начнёт цитировать собственные прошлые ответы как источники.
```

### 4. Верификатор не вызывает LLM

```python
# ✅ ПРАВИЛЬНО — регэксп + запрос в базу + нормализованное сравнение строк.
# ❌ ЗАПРЕЩЕНО — «пусть модель проверит, правда ли это».
```

### 5. Русская морфология — префиксные запросы

```python
# ✅ ПРАВИЛЬНО — FTS5 unicode61 + префикс:
fts_query = " ".join(f"{token}*" for token in tokens)   # "обесценива*"

# ❌ НЕПРАВИЛЬНО — точное совпадение словоформы: найдёт «обесценивание»,
# но не «обесценивания». Чередования (искать/ищу) префикс не покрывает —
# лечится синонимами в промпте, лемматизация — опционально и потом.
```

### 6. Программа обязана работать без модели

Экран «Поиск», подключение архива, просмотр постов — всё это работает,
когда модель не настроена вообще. Ни один из этих путей не должен падать
или блокироваться из-за отсутствия LLM.

### 7. Бюджеты цикла — обязательны

```python
MAX_STEPS = 12          # шагов агентного цикла
MAX_TOKENS_PER_SESSION  # лимит токенов
TIMEOUT_SECONDS         # таймаут

# При превышении — НЕ падать, а вернуть частичный ответ с пометкой
# «поиск прерван по лимиту, вот что найдено».
```

### 8. Лог шагов — первоклассная сущность

Каждый `tool_call` с параметрами и длительностью пишется в `turns`
и стримится в UI через WebSocket. Не «для отладки» — это видимая
пользователю функция «как я искал».

### 9. Указывать путь файла (ОБЯЗАТЕЛЬНО)

```
FILE: core/tools/search.py
FILE: agent/verifier.py
```

### 10. Конвенция `__init__.py`

При создании **любой** новой папки — сразу создавать `__init__.py` с комментарием.

### 11. Перед патчем — проверь контекст

Прежде чем писать патч, прочитай текущее состояние файла. Не предполагай, что код
выглядит как в прошлом патче или как ты его оставил — между сессиями могли быть
ручные правки. **Старый код в памяти ≠ текущий код на диске.**

### 12. После патча — проверь ссылки

После каждого патча проверяй целостность: все имена, на которые ссылается изменённый
код, должны существовать. Переименовал — сделай grep по проекту на старое имя.
Добавил вызов — убедись, что цель существует с той же сигнатурой.

### 13. Не расширять зону работ без спроса

Если по ходу задачи обнаружилась смежная проблема — **сообщить, а не чинить молча**.
Записать в `librarian_статус.md` → «Застряло / вопросы к себе». Причина: иначе
патч разрастается, и непонятно, что именно сломало сборку.

### 14. Smoke-тест перед каждым релизом — ОБЯЗАТЕЛЬНО

**Урок из Parser v1.7.2:** три регрессии прошли незамеченными больше месяца,
потому что тестировались только сценарии из чейнджлога, а не смежные пути.

Обязательный минимум (5 минут):

1. **Запуск без модели** — программа стартует, архив подключается, поиск работает
2. **Поиск** — русский запрос со словоформой (`обесценивание` находит `обесценивания`)
3. **Просмотр поста** — клик по результату открывает пост с подсветкой
4. **Диалог с моделью** — один вопрос, в логе видны шаги, в ответе есть ссылки
5. **Верификатор** — сфабрикованная ссылка `[пост 999999]` помечается как ⚠
6. **Ловушка** — вопрос про то, чего в архиве нет → честный ответ «не нашёл»
7. **База Parser не изменилась** — сверить mtime и размер файла до/после

**Если что-то из этого не работает — релиз СТАВИТСЯ НА ХОЛД.**
Пункт 5 и пункт 7 не пропускать никогда: это два главных обещания продукта.

## 🩹 ФОРМАТ ПАТЧА (патч-скрипты)

Все изменения кода передаются **самоприменяющимся Python патч-скриптом**,
запускаемым из корня проекта. Никогда не присылать полные файлы исходников.

### Требования к патч-скрипту

1. **OLD → NEW блоки** с точными строковыми якорями. Якорь не найден или найден
   не один раз → громкий fail с понятным сообщением, файл НЕ трогается.
2. **Идемпотентность** — повторный запуск определяет «уже применено» и выходит с OK.
3. **CRLF сохраняется** — читать байтами, нормализовать в `\n` для поиска,
   при записи восстановить исходные окончания строк.
4. **`py_compile` после применения** — синтаксис проверяется до передачи пользователю.
5. Для больших методов допустим поиск по границам класса, но не «жадный» regex.

### Строковые литералы с `\n` — двойное экранирование

Если вставляемый код содержит `\n` внутри строк, в патч-скрипте пишется `"\\n"`.
Иначе Python запишет реальный перевод строки → SyntaxError в целевом файле.

### Выбор подхода

| Ситуация | Подход |
|----------|--------|
| Замена тела метода | Читать файл → границы класса → заменить от `def` до `def` |
| Добавление нового метода | Вставить после известного якоря |
| Удаление метода | Найти границы → удалить строки программно |
| Строки с `\n` | Всегда `"\\n"` в патч-скрипте |
| Мелкие правки (1–2 строки) | Ручное исправление — быстрее и надёжнее |
| Правка SQL-схемы | Отдельная миграция + `PRAGMA user_version`, не «пересоздать базу» |

### Пример минимального патч-скрипта

```python
# patch_example.py — запускать из корня проекта
import py_compile, sys
from pathlib import Path

FILE = Path("core/tools/search.py")

OLD = '''    return results[:20]'''
NEW = '''    return results[:MAX_RESULTS]'''

raw = FILE.read_bytes().decode("utf-8")
crlf = "\r\n" in raw
src = raw.replace("\r\n", "\n")            # нормализация для поиска

if NEW in src:
    print("Уже применён — выходим (идемпотентность)"); sys.exit(0)
if src.count(OLD) != 1:
    sys.exit(f"ЯКОРЬ НЕ НАЙДЕН (или найден не один раз) в {FILE} — патч не применён")

src = src.replace(OLD, NEW, 1)
out = src.replace("\n", "\r\n") if crlf else src   # восстановление CRLF
FILE.write_bytes(out.encode("utf-8"))

py_compile.compile(str(FILE), doraise=True)
print("OK: патч применён, синтаксис проверен")
```

## 🔄 Основные потоки выполнения

### Подключение архива:
```
UI: выбор папки / автопоиск в output/
  → passport.read(archive_passport.json)
  → parser_db.open(mode=ro) → PRAGMA user_version → capability-check (v1/v2)
  → fts.build_or_update()
  → UI: карточка архива готова
```

### Поиск без ИИ («читальный зал»):
```
UI: строка запроса
  → tools.search(query) → ≤ 20 сниппетов
  → UI: список результатов
  → клик → tools.read_post(post_id) → просмотр с подсветкой
```

### Вопрос с моделью (основной сценарий):
```
UI: вопрос «Как прорабатывается обесценивание?»
  → classifier: {mode: "Архивариус", task: "Вопрос-ответ"}
  → orchestrator: промпт(шаблон режима + паспорт + блокнот)
    → llm → tool: search("обесценива*")   → 14 сниппетов   ─┐

    → llm → tool: read_post(127)          → текст           │ каждый шаг → WebSocket → UI
    → llm → финальный ответ со ссылками                    ─┘
```
